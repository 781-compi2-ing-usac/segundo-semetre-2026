## 1. ¿Qué es PLY?

**PLY (Python Lex-Yacc)** es una implementación en Python puro de los clásicos generadores de compiladores **lex** y **yacc** de Unix. Son dos módulos independientes que casi siempre se usan juntos:

- `ply.lex` → convierte texto plano en una secuencia de **tokens** (análisis léxico).
- `ply.yacc` → toma esos tokens y construye una estructura (típicamente un AST) según una **gramática**, usando el algoritmo **LALR(1)** (análisis sintáctico).

La diferencia principal frente a otras herramientas que ya conocen (como ANTLR4) es que en PLY la gramática y las reglas léxicas se escriben usando **convenciones de nombres de funciones/variables** dentro de código Python normal, no un lenguaje de gramática separado. PLY usa introspección (`inspect`) sobre tu módulo para armar las tablas de análisis.

## 2. `ply.lex` — El analizador léxico

### 2.1 Estructura mínima

```python
import ply.lex as lex

# 1. Lista de nombres de tokens (obligatorio)
tokens = (
    'NUMBER',
    'PLUS',
    'MINUS',
    'TIMES',
    'DIVIDE',
    'LPAREN',
    'RPAREN',
)

# 2. Reglas simples: variable t_NOMBRE = regex como string
t_PLUS    = r'\+'
t_MINUS   = r'-'
t_TIMES   = r'\*'
t_DIVIDE  = r'/'
t_LPAREN  = r'\('
t_RPAREN  = r'\)'

# 3. Reglas complejas: función t_NOMBRE(t) cuando necesitas lógica
def t_NUMBER(t):
    r'\d+'
    t.value = int(t.value)  # convertir de string a int
    return t

# 4. Caracteres a ignorar (espacios, tabs)
t_ignore = ' \t'

# 5. Contar saltos de línea (para reportar errores con número de línea)
def t_newline(t):
    r'\n+'
    t.lexer.lineno += len(t.value)

# 6. Manejo de errores léxicos
def t_error(t):
    print(f"Carácter ilegal '{t.value[0]}' en línea {t.lexer.lineno}")
    t.lexer.skip(1)

# 7. Construir el lexer
lexer = lex.lex()
```

### 2.2 La convención de nombres `t_`

PLY no usa un archivo de configuración separado para el lexer: usa **introspección** sobre tu propio módulo de Python. Cuando llamas a `lex.lex()`, PLY recorre todo tu archivo buscando **todo lo que empiece con el prefijo `t_`** (ya sea una variable o una función) y con eso arma el lexer automáticamente.

Por eso el prefijo `t_` es obligatorio para todo lo que quieras que el lexer reconozca:

- `t_ignore` → caso especial: caracteres a ignorar (no es un token).
- `t_error` → caso especial: función que maneja errores léxicos (no es un token).
- `t_newline` → convención común para contar líneas; normalmente no hace `return t` porque no queremos que el salto de línea llegue como token al parser.
- Cualquier otro `t_NOMBRE` → PLY asume que `NOMBRE` es un token y que **debe estar declarado en la tupla `tokens`**.

**Importante:** si escriben algo sin el prefijo `t_` (por ejemplo `token_PLUS` en vez de `t_PLUS`), PLY no da ningún error — simplemente lo ignora silenciosamente, y esa regla nunca se ejecuta. Es uno de los bugs más comunes y difíciles de detectar al empezar, porque el programa "corre" pero el lexer no reconoce ese carácter/símbolo. Si a un estudiante "no le está funcionando" un token, lo primero que hay que revisar es que el nombre de la función/variable empiece exactamente con `t_`.

### 2.3 La `r` antes del string: raw strings, no regex

Un punto que suele confundir: la `r` en `r'\+'` **no es parte de PLY ni de las expresiones regulares** — es una característica del propio lenguaje Python, llamada **raw string**.

Normalmente, Python interpreta la barra invertida (`\`) dentro de un string como el inicio de una secuencia de escape: `'\n'` se convierte en un salto de línea real, `'\t'` en un tab, etc. Un raw string (`r'...'`) le dice a Python: *"no interpretes las barras invertidas, déjalas tal cual, literales"*.

¿Por qué esto importa para las expresiones regulares? Porque las regex **también** usan `\` para sus propios fines (`\d` = dígito, `\+` = el signo `+` literal, `\.` = punto literal, etc.). Si se escribiera `'\d'` sin la `r`, Python podría alterar esa secuencia antes de que el motor de regex la reciba. Con `r'\d'`, Python entrega el string sin modificar (los dos caracteres `\` y `d`) al motor de regex (el módulo `re` de Python, que PLY usa internamente), que sí lo interpreta correctamente como "un dígito".

**Resumen:** la `r` resuelve un problema de Python (evita que interprete el `\` antes de tiempo); lo que va **dentro** de las comillas es lo que el motor de regex interpreta.

### 2.4 Expresiones regulares: lo esencial para el lexer

Las reglas léxicas de PLY (tanto `t_NOMBRE = r'...'` como el docstring de las funciones `t_NOMBRE(t)`) son expresiones regulares estándar de Python (módulo `re`). No hace falta dominar todo regex, pero sí estos conceptos:

**Metacaracteres que SÍ necesitan escape (`\`) porque tienen significado especial:**

| Carácter | Significado en regex | Cómo escribirlo literal |
|---|---|---|
| `+` | uno o más | `\+` |
| `*` | cero o más | `\*` |
| `?` | cero o uno (opcional) | `\?` |
| `.` | cualquier carácter | `\.` |
| `(` `)` | agrupación | `\(` `\)` |
| `[` `]` | conjunto de caracteres | `\[` `\]` |
| `{` `}` | cantidad exacta de repeticiones | `\{` `\}` |
| `|` | "o" (alternancia) | `\|` |
| `^` | inicio de línea (o negación dentro de `[ ]`) | `\^` |
| `$` | fin de línea | `\$` |
| `\` | el propio backslash | `\\` |

**Caracteres que NO necesitan escape porque no son especiales por sí solos:**

- `-` (guion) → solo tiene significado especial **dentro** de corchetes, para indicar un rango (`[a-z]`). Fuera de corchetes es literal, por eso `t_MINUS = r'-'` funciona sin problema.
- Letras, números, `_`, espacios → siempre literales.

**Clases de caracteres útiles para el proyecto (OxigenScript):**

| Patrón | Significa |
|---|---|
| `\d` | un dígito (`0-9`) |
| `\d+` | uno o más dígitos (un número entero) |
| `[a-zA-Z_]` | una letra o guion bajo |
| `[a-zA-Z_][a-zA-Z_0-9]*` | patrón típico de identificador: empieza con letra/guion bajo, sigue con letras/dígitos/guion bajo |
| `\d+\.\d+` | un número decimal simple (ej. `3.14`) |
| `"[^"]*"` | un string entre comillas dobles, sin comillas dentro (`[^"]` = "cualquier carácter que no sea comilla") |
| `//.*` | un comentario de una línea (típico en lenguajes tipo C/Rust): `//` seguido de cualquier cosa hasta el final de la línea |
| `\n+` | uno o más saltos de línea |

**Cuantificadores:**

| Símbolo | Significa |
|---|---|
| `*` | 0 o más repeticiones |
| `+` | 1 o más repeticiones |
| `?` | 0 o 1 repetición (opcional) |
| `{n}` | exactamente n repeticiones |
| `{n,m}` | entre n y m repeticiones |

**Consejo práctico:** antes de conectar el lexer con el parser, prueben sus patrones aislados en Python:

```python
import re
print(re.match(r'[a-zA-Z_][a-zA-Z_0-9]*', 'variable_1'))
```

Esto ayuda a que los estudiantes depuren regex sin tener que correr todo el pipeline de PLY, y es exactamente lo mismo que recomendamos antes con `lexer.input(...)` para probar el lexer completo de forma aislada.

### 2.5 Reglas clave que hay que entender

**Orden de evaluación de las reglas:**
- Las reglas definidas como **funciones** se prueban en el **orden en que aparecen** en el archivo.
- Las reglas definidas como **strings** (`t_PLUS = r'...'`) se ordenan automáticamente por **longitud de la expresión regular** (la más larga primero).

Esto es una fuente común de bugs: si necesitan identificar palabras reservadas (`if`, `while`, `fn`), **no** las definan como tokens de string separados — hay que capturarlas dentro de la función `t_ID`, comparando contra un diccionario.

**Patrón para palabras reservadas:**

```python
reserved = {
    'if': 'IF',
    'while': 'WHILE',
    'fn': 'FN',
}

tokens = ['ID', 'NUMBER'] + list(reserved.values())

def t_ID(t):
    r'[a-zA-Z_][a-zA-Z_0-9]*'
    t.type = reserved.get(t.value, 'ID')  # si no está en reserved, es un ID normal
    return t
```

**Probar el lexer de forma aislada** (antes de meterse con el parser):

```python
lexer.input("3 + 4 * (2 - 1)")
for tok in lexer:
    print(tok)
```

Esto es clave para que los estudiantes depuren su lexer por separado antes de conectar el parser.

## 3. `ply.yacc` — El analizador sintáctico

### 3.1 Estructura mínima

```python
import ply.yacc as yacc

# Necesita los tokens definidos en el lexer
from lexer import tokens

# 1. Precedencia y asociatividad de operadores
precedence = (
    ('left', 'PLUS', 'MINUS'),
    ('left', 'TIMES', 'DIVIDE'),
)

# 2. Reglas gramaticales (docstring = regla en notación BNF-like)
def p_expression_binop(p):
    '''expression : expression PLUS expression
                  | expression MINUS expression
                  | expression TIMES expression
                  | expression DIVIDE expression'''
    if p[2] == '+':
        p[0] = ('binop', '+', p[1], p[3])
    elif p[2] == '-':
        p[0] = ('binop', '-', p[1], p[3])
    elif p[2] == '*':
        p[0] = ('binop', '*', p[1], p[3])
    elif p[2] == '/':
        p[0] = ('binop', '/', p[1], p[3])

def p_expression_group(p):
    'expression : LPAREN expression RPAREN'
    p[0] = p[2]

def p_expression_number(p):
    'expression : NUMBER'
    p[0] = ('num', p[1])

# 3. Manejo de errores sintácticos
def p_error(p):
    if p:
        print(f"Error de sintaxis en '{p.value}', línea {p.lineno}")
    else:
        print("Error de sintaxis: fin de archivo inesperado")

# 4. Construir el parser
parser = yacc.yacc()
```

### 3.2 Conceptos clave

**`p[0]`, `p[1]`, `p[2]`...** representan los símbolos de la regla en orden:
- `p[0]` es lo que esta regla **produce** (el resultado).
- `p[1]`, `p[2]`, ... son los símbolos del lado derecho de la regla, en el mismo orden en que aparecen en el docstring.

Aquí es exactamente donde se construyen los **nodos del AST** — pueden ser tuplas simples (como en el ejemplo), diccionarios, o (recomendado para el proyecto) instancias de clases de nodo definidas en un módulo aparte (`ast_nodes.py`).

**`precedence`** resuelve ambigüedades de tipo shift/reduce (qué operador "gana" y en qué orden se asocian). Si la quitan, PLY va a generar warnings de conflictos shift/reduce en consola — vale la pena mostrarles ese mensaje intencionalmente para que aprendan a leerlo.

**Archivos generados automáticamente:**
- `parser.out` — `yacc.yacc()` lo genera automáticamente porque `debug=True` es el valor **por defecto** (no hay que activarlo, ya viene así); contiene la tabla de estados LALR completa. Muy útil para conectar la teoría (ítems LR, closure, goto) con lo que realmente está pasando. Si quieren desactivarlo, sería `yacc.yacc(debug=False)`.
- `parsetab.py` — tabla de parsing cacheada para no reconstruirla en cada ejecución.

Ambos van en `.gitignore`, no son código fuente.

### 3.3 Unir lexer + parser

```python
data = "3 + 4 * (2 - 1)"
result = parser.parse(data, lexer=lexer)
print(result)
```

## 5. Errores comunes al empezar con PLY

| Síntoma | Causa probable |
|---|---|
| `Token 'X' defined, but not used` | Está en `tokens` pero ninguna regla lo genera |
| `Rule 'X' defined, but not used` | Regla de gramática que ningún otro símbolo referencia (no alcanzable desde el símbolo inicial) |
| Conflictos shift/reduce en consola | Falta o está mal definida la tabla de `precedence` |
| El parser no reconoce nada | El lexer y el parser no comparten la misma lista `tokens` |
| Cambios al lexer/parser no se reflejan | `parsetab.py` cacheado desactualizado — bórrenlo y vuelvan a correr |
